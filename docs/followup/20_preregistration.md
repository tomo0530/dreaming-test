## 1. 条件の表記

## 2. 主仮説（固定順序）

| 順 | 仮説 | 推定量 Δ = mean_s[…] |
|---|---|---|
| H1 | 採点フィードバックは Dreaming を改善する | acc_s(`fb1/A4`) − acc_s(`fb0/A4`) |
| H2 | フィードバックがあれば、Dreaming は記憶なしを上回る | acc_s(`fb1/A4`) − acc_s(`fb1/A0`) |
| H3 | フィードバックがあれば、Dreaming は Rolling Summary を上回る | acc_s(`fb1/A4`) − acc_s(`fb1/A1`) |

- **区間**: ストリームを再標本化の単位とする paired bootstrap（10,000 回、パーセンタイル法 95% CI、乱数 seed 20261111）。
- **判定**:
  - CI 下限 > 0 → 支持。両側 95% CI の下限で判定するので、片側の有意水準は 2.5% にあたる。
  - CI が 0 を含む → 「示せない」。「同等」とは書かない。
  - CI 上限 < 0 → 「逆向き」。
- **固定順序**:
  - H1 が支持されたときだけ、H2 を確証的に判定する。H2 が支持されたときだけ、H3 を確証的に判定する。
  - 判定に進まなかった仮説は、推定値と CI を「探索的」として報告する。
  - この手順により、主仮説の族全体の第一種の過誤は片側 2.5% 以下に抑えられる。
- **確証的判定の前提**:
  - `failed` と `interrupted` のジョブは、解析の前に `--resume` で完走させる。
  - 確証的に判定するのは、40 ストリームすべてで 6 条件（`fb0`・`fb1` × A0・A1・A4）が完走した場合だけとする。
  - 1 本でも欠けた場合（予算到達などで完走できなかった場合）は、3 つとも探索的に報告し、§5 の欠測の感度分析を並べる。処置に依存した除外で判定が偏るのを避けるためである。
- **実務上の目安**: Δ ≥ +0.05。点推定と並べて示すが、判定には使わない。
- **主張の範囲**:
  - A1・A4 は、回答後のメモ作成を強制した「記憶システム全体」として比べる（前回の A1・A4 とは別の処置）。
  - フィードバックは transcript にだけ書かれる。したがって、H1 の効果は統合（オフライン処理）を通じたものに限られる。

## 3. 副次指標と探索的分析（主張には使わない。補正なし）

- **副次**:
  - 交互作用 [acc(`fb1/A4`) − acc(`fb0/A4`)] − [acc(`fb1/A1`) − acc(`fb0/A1`)]。ストリームごとに差の差を取り、同じ bootstrap で CI を出す。
  - A/A 検査 acc(`fb1/A0`) − acc(`fb0/A0`)。
    - A0 にはフィードバックの経路がないので、真の差は 0 である。
    - CI が 0 を含まない場合は、同時に走らせた run の間に系統的な揺らぎがあったと記録する。主仮説の判定は変えないが、レポートで H1 の解釈に添える。
- **群の差**:
  - `fb0/A4` − `fb0/A1`、`fb0/A4` − `fb0/A0`、`fb0/A1` − `fb0/A0`、`fb1/A1` − `fb0/A1`
  - `fbX/A2` − `fbX/A0`（X = 0, 1）。`fb1/A2` はフィードバック行を検索で読める（00_design F17）。
  - `fb0/A5` − `fb0/A0`
- **層別**:
  - drift 依存かどうか、セッション帯（1〜4、5〜8、9〜12）。
  - drift 種別（`soft_delete`、`stale_table`、`unit`、`status_code`、`column_name`、`join_key`）。
    - 問題の drift 種別は、問題のエポックが 2 以上のときに、その問題の `fact_ids` が指す Fact のうち、問題のエポックで値が変わった（`valid_from_session` がそのエポックの開始セッションに等しい）Fact の `kind` とする。エポック 1 の問題は drift 種別を持たない。この定義は、既存の `drift_dependent` 判定と一致することをテストで確かめる。
    - 複数あれば、それぞれの種別に数える。該当する Fact がなければ「drift 非依存」とする。
- **機構実験**（ストリーム `fu-01`〜`20`）:
  - 交互作用 [acc(`verify/A4`) − acc(`fb0/A4`)] − [acc(`verify/A0`) − acc(`fb0/A0`)]。A1 も同じ形で出す。
  - 行動指標（§4）の同じ形の差。
- **A4+probe**: acc(`probe/A4`) − acc(`fb0/A4`)（ストリーム `fu-01`〜`20`）。行動指標と、§4 の「void 列に言及する禁止・否定表現の行数」も比べる。
- **drift のない対照**:
  - `null/A1`・`null/A4` の memory probe の正答率。drift がないので、gold の Fact は全セッションで変わらない。誤答は、記憶に誤った事実があることを示す客観的な指標になる。
  - §4 の「変更の記述」の数。`fb0` の同じ群（drift あり）の値と並べて示す記述統計とする。
- **CL-Bench**: 前回の 3 反復（`clbench-r0`〜`r2`）と追試の 15 反復（`r3`〜`r17`）を合わせた 18 反復で、A4 − A1 と A4 − A0 の公式 score と正答率の差を出す。
- **その他**: 1 正答あたりの費用、誤答分類、`note_written` 率、`retrieved_tokens`、統合役の照会回数。
- **感度分析**（`fu_sens` を実行した場合）: `sens/A4` − `sens/A1`、`sens/A4` − `sens/A0` と、`fb0` の同じストリームの値との比較。

## 4. 機械的な指標の定義

すべて transcript・結果行・記憶スナップショット・`stream.json` からコードで数える。judge は使わない。SQL の判定は、小文字化し、連続する空白を 1 つにした文字列に対して行う。照会は「成功した `query`」（tool 結果が `ERROR:` で始まらないもの）だけを数える。

- **1 問あたりのクエリ数**: 成功した照会の数（`QuestionResult.ok_queries`）。
- **参照表の無条件照会**: その問題の成功した照会のうち、少なくとも 1 つが次をすべて満たす。前回の診断の「コード表の全件確認」に対応する行動指標だが、返却された値を agent が確認したことまでは意味しない。
  - そのストリームの参照表（`ref_codes`・`code_lookup`・`lkp_values` のうち、エポック 1 の DB に実在するもの）を `from <参照表>` または `join <参照表>` で参照している。
  - `where`・` on `・`limit` のいずれも含まない。
  - `sqlite_master` と `pragma` を含まない。
  - 集約関数（`count(`、`sum(`、`min(`、`max(`、`avg(`）と `group by` を含まない。
- **スキーマ確認**: その問題の成功した照会のうち、少なくとも 1 つが `pragma` で始まる、または `from sqlite_master` を含む。
- **変更の記述**（drift のない対照の記述統計）:
  - 対象は、各セッション後のスナップショット `snapshots/session_{k}/memory/injected.md`（k = 1〜11）の各行。
  - 次の正規表現（大文字小文字を区別しない）のどちらかに一致し、かつ否定語 `\b(no|not|never|without|unchanged)\b` を含まない行を数える。
    - 変更履歴の形: `\b(was|were|changed|renamed|moved|replaced|switched)\b.*\bs(ession )?\d+\b`
    - 競合の記録: `^\s*[-*]?\s*CONFLICT:`
  - ストリーム・群ごとに、スナップショットあたりの平均行数を指標とする。
  - drift のないストリームでも、行の追加と void 行の物理削除は起きる。そのため、一致した行がすべて事実に反するとは解釈しない。
- **void 列に言及する禁止・否定表現の行数**（A4+probe の比較用）:
  - 対象は、soft delete が有効なエポックに入った後のスナップショット。
  - void 列の名前は、そのストリームの `stream.json` で `kind == "soft_delete"` の Fact の `value`（例: `ord_hdr.void_flg = 1`）にある最初の `<表>.<列>` 形式の識別子の、列の部分とする。
  - その列名を含み、かつ `\b(do not|don't|never|avoid|should not|must not|no need)\b` を含む行を数える。
  - 「除外する」「除外しない」のどちらの方針か、また正誤は解釈しない。記述の量の比較だけに使う。

## 5. 固定する実験条件

| 項目 | 値 |
|---|---|
| 群と run | 00_design §6 の表のとおり |
| セッション / 問題 | 12 セッション × 6 問（全 72 問）。migration はセッション 4・8 の後（drift のないストリームを除く） |
| 偽メモ注入 | なし |
| モデル | 全役割 `gpt-6-luna`。agent `reasoning_effort=low`、統合役 `medium`（`fu_sens` の agent だけ `medium`） |
| 予算 | 各 `configs/experiments/followup/*.yaml` の `budgets` をそのまま使う。主条件の run は phase `fu_main`（$52）、探索的な run は phase `fu_aux`（$25） |
| 解析対象 | 各比較に必要なすべての条件が完走したストリームだけを使う。主仮説の 3 つと副次指標は、6 条件（`fb0`・`fb1` × A0・A1・A4）がすべて完走したストリームで計算する。1 条件でも完走しなかったストリームは、その比較のすべての条件から除外する |
| 除外の報告 | 除外したストリームの数を、理由（`failed`、`budget_exhausted`、`interrupted`）と条件ごとに報告する |
| 欠測の感度分析 | 除外したストリームについて、比較に必要な全条件で完了したセッションの問題だけを加え、主仮説の推定量を計算し直して並べて示す（判定には使わない） |
| 未提出の扱い | 完走したストリームで、1 問の上限に達して提出がなかった問題は `no_submission` の誤答として分母に含める |
| 停止規則 | phase の枠または累計の絶対上限 $200 に達したら、その phase で新しいストリームを始めない。その時点で完走したストリームだけで解析する |
