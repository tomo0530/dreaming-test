## 1. 本実験の参考結果（逸脱のもとで実施。§0 を参照）

1. **主仮説 H1 は支持されなかった。** 差 Δ = acc(A4) − acc(A1) は **−1.1pt**、95% CI は **[−4.2, +2.2]** だった。CI が 0 をまたぐため、事前登録の判定は「A4 の優位を示せない」となる。CI の上限 +2.2pt は、実務上の目安 +5pt を下回る（判定には使わない補足）。A1 が上回ったとも言えない。ストリーム単位では、A4 の 10 勝 9 敗 1 分けだった。
   - **注意:** 本実験は、事前に定めた開始条件（pilot gate）を満たさないまま、逸脱として実施した（§8 の 1）。計画の改訂手順を事後に実施しても、gate は不合格だった（§8 の 6）。計画の規則に従えば、この研究は「条件の構築まで」で閉じる結果である。H1 の判定は、この前提のもとで読む必要がある。
2. **探索的には、記憶を持つ群が記憶なし（A0）を下回った。** 差は A4 − A0 が −6.1pt [−8.5, −3.7]、A1 − A0 が −5.0pt [−7.8, −2.3]、A3 − A0（事後に追加）が −3.75pt [−5.5, −2.2] だった（補正なし）。事後の層別では、A1・A4 の差は migration 後の drift 依存の問題に集中し、drift 非依存の問題ではほぼ 0 だった（§4）。
3. **最も有力な説明は「記憶があると DB の値の確認が浅くなる」こと（事後の観察で、因果は未検証）。** 記憶群は、記憶にあるコード表名で絞り込んで照会するか、コード表をまったく読まなかった。そのため、migration で追加された無効化フラグ（soft delete）を見落とす傾向があった。オフライン処理はスキーマの変化には気づいていた。ただし、採点結果を知らないまま、エージェント自身の回答方針（「void 列で除外しない」など）を規則として書いた例があった。
4. **妥当性の制約: 提示した記憶ツールの一部が、オンラインではまったく使われなかった。** A2 は `search_transcripts` を 1,440 問中 0 回、A3・A4 は `memory_write` を 2,880 問中 0 回しか呼ばなかった。このため、A2 は実質的に検索のない A0 と同じ振る舞いになった（正答率 0.835 と 0.826）。A3・A4 の notes 層も空のままだった。「Raw-RAG の効果」と「オンラインのメモ書き＋オフライン検証」という設計上の対比は、この実験では検証できていない。
5. **偽メモの実害と訂正（探索的）。** transcript を読めない A3 では、偽メモが記憶に残り続けた。注入対象の問題（Q_inj）では 120 問中 31 問が誤答（wrong_result 30、no_submission 1）し、wrong_result のうち 25 問は偽のコードを使った SQL だった（A0 の Q_inj 正答率は 0.975）。A1・A4 では、自動判定で 40 件中 39〜40 件が「訂正」と判定された。ただし A3 には偽メモと食い違う情報源がそもそもなかった。そのため、訂正できた理由を「transcript を読めること」だけに帰属させることはできない（§5）。
6. **CL-Bench でも、A4 と A1 の差は示せなかった。** score の差 A4 − A1 は −0.019 で、CI は [−0.17, +0.19]（n = 3）と幅が広く、同等とも言えない。記憶群は A0 より高く（A4 − A0 = +0.215、A1 − A0 = +0.234）、3 反復すべてで差は正だった。「記憶があると改善する」という向きは記事と一致した。
7. **費用の合計は $10.57**（予算 $100〜200 の約 1/10）。本実験は $7.89 だった。本実験の後に E2 の改訂手順を事後に実施し（$1.28、gate はやはり不合格。§8 の 6）、それを含めた累計は $11.85 である。

### 4.2 transcript の診断（`main-diagnosis.md`）

stale 誤答の全件（A0 86、A1 130、A2 95、A3 102、A4 143、A5 12）と drift 依存の全問題を、スクリプトで集計した。soft delete の失敗約 14 件と stale table の失敗 9 件は、手で読んだ。以下は観察された関連であり、因果は検証していない。

**drift の種類別の stale 誤答**（その時期に変わった drift の種類ごと。1 問が複数の種類に当たる場合は重複して数えた）

| drift の種類 | 問題数 / 群 | A0 | A1 | A2 | A3 | A4 | A5 |
|---|---|---|---|---|---|---|---|
| soft delete（無効化フラグ列とコード表の追加） | 113 | 8 | 32 | 5 | 8 | 45 | 6 |
| stale table（旧テーブルが凍結されて残り、新テーブルに移る） | 119 | 50 | 69 | 56 | 64 | 57 | 6 |
| unit（金額の単位の変更） | 132 | 28 | 22 | 34 | 30 | 39 | 0 |
| status code（コード値の変更） | 192 | 0 | 6 | 0 | 0 | 2 | 0 |

- 列名や結合キーの変更（照会がエラーになる「目立つ」drift）では、どの群もほぼ誤答しなかった。
- **差の大部分は soft delete に集中していた。**
  - soft delete の問題の正答率は、A0 0.91、A2 0.92、A3 0.88、A5 0.89 に対し、A1 0.44、A4 0.40 だった。
  - A0 との正答数の差（A4 は 88 問、A1 は 72 問）のうち、soft delete が A4 では 58 問（66%）、A1 では 53 問（74%）を占める。
- **スキーマの確認は、どの群も行っていた。** `sqlite_master` などによる確認は、どの群でも 95〜100% の問題で行われていた。
- **減っていたのは値の確認だった。**
  - コード表を `code_set` で絞り込まずに全件表示した割合は、A0 84〜90%、A2 85〜91%、A3 80〜85% だった。これに対し、A4 は 41% → 25% → 22%、A1 は 30% → 19% → 15% と下がった（migration 前 → 1 回目の後 → 2 回目の後）。
  - soft delete の問題 113 問で A4 がコード表をどう読んだかを分けると、読まなかった 85 問、絞り込んで読んだ 13 問、全件を読んだ 15 問だった。正答率は、全件を読んだ場合 0.80、読まなかった場合 0.32 だった。
  - 典型例は `main-01` の A4 の s09q3（4 月以降の注文数）である。A4 はコード表を読まずに提出し、void 列による除外を入れなかった。
- **drift 直後から差が出ていた。** 記憶に void 列の記述がまだない、drift 直後のセッションでも、soft delete の正答率は A1・A4 0.48、A0 0.92 だった。したがって、古い事実を記憶していたことは主な説明にならない。
- **オフライン処理は変化に気づくが、誤った方針を書くことがあった。**
  - A4 は s12 の probe で、drift 後の事実に 45 / 50 正答した。構造の変化は記憶に取り込まれていた。
  - 一方で、エージェント自身の回答から方針を書いた例がある。例: `main-01/A4/snapshots/session_009/memory/injected.md`（s9 の後の注入層。s10 で使われた）の "Do not add a `void_flg` exclusion by assumption"。s10 の s10q6 は stale になった。
  - void 列について「除外しない／意味不明」と書かれていたセッションの soft delete 正答率は、A4 0.07（n = 28）、A1 0.08 だった。「除外する」と書かれていたセッションでは、A4 0.62、A1 0.65 だった。
- **stale table は A0 でも難しかった。** A0 の正答率も 0.46 と低い。A0 に対して記憶群が上乗せした誤答は、A1 で 15 問、A4 で 5 問にとどまる。
- **後半の低下は、drift 依存の問題に限られる。**
  - s9〜12 の drift 非依存の問題では、正答率は A4 0.86、A0 0.89 でほぼ同じだった。
  - soft delete が 2 回目の migration（s9）で入るストリームは、該当 12 本のうち 8 本あった。
  - 注入層の大きさは平均 750〜1,000 token、最大 1,829 で、上限 2,000 には届かなかった。切り詰めは起きていない。

## 5. 偽メモ注入（探索的な診断）

事前登録 §0 のとおり、注入関連の指標は、記憶層の汚染と訂正の挙動を観察する診断として扱う。Δ の原因を訂正能力に帰属させる主張には使わない。

**指標の定義**（`evaluation/summary.py`）
- 偽メモは、セッション 3 と 7 のオンラインが終わった直後に注入した。
- 「訂正」は、次の 2 条件を両方満たした場合とした。
  - 注入後の最初の probe（セッション 4 または 8 の後）より前の最後のオフライン処理（注入後 2 回目）の時点で、記憶から偽メモの marker と偽の主張が検出されない。
  - その probe で、注入対象の事実に正答する。
- 「残存率」は、注入後のオフライン処理のうち、偽メモが検出された回の割合である。

| 群 | 注入数 | 訂正数（訂正率） | 残存率（自動判定） | 注入対象の probe 正答率 | Q_inj（偽メモ検出あり） | Q_inj（検出なし） |
|---|---|---|---|---|---|---|
| A1 | 40 | 39（0.975） | 0.029 | 1.00 | 4 / 5 正答 | 109 / 115 正答 |
| A3 | 40 | 0（0.0） | 1.000 | 0.00 | 89 / 120 正答 | — |
| A4 | 40 | 40（1.0） | 0.029 | 1.00 | 5 / 5 正答 | 108 / 115 正答 |

- **A3 では実害があった。** 偽メモが残った状態の Q_inj で 31 問が誤答（wrong_result 30、no_submission 1）し、wrong_result のうち 25 問は偽のコードを使った SQL だった。pilot（1 ストリーム）では、偽メモによる誤答は 0 件だった。
- **検出器には誤検出がある**（R2 レビューでの目視確認）。

## 9. 示せたこと / 示せていないこと

**示せたこと**
- この設定（`gpt-6-luna`、SQL agent、12 セッションのうち 2 回の migration）では、Verified Dreaming（A4）が Rolling Summary（A1）を上回るとは言えない。+5pt 以上の優位とも整合しない。
- この設定では、記憶を持つ群は記憶なしより正答率が低かった（探索的、補正なし）。A1・A4 の低下は、スキーマが変わった後の問題に集中していた（事後）。
- transcript を読めない記憶整理（A3）では、注入した偽メモが残り、Q_inj の誤答につながった（探索的）。

**示せていないこと**
- 事前に定めた開始条件を満たした状態での H1 の検証。本実験は gate が不合格のまま、逸脱として実施した。改訂手順を事後に実施しても、gate は不合格だった（§8 の 1・6）。
- A4 と A1 が同等であること（CI の幅は ±3〜4pt）。
- 記憶群が劣った理由の因果。「値の確認が浅くなる」「採点のない統合が誤った方針を書く」は、事後の観察に基づく最も有力な説明にとどまる。
- Raw-RAG（A2）の効果。エージェントが検索ツールを使わなかったため、A2 は実質的に A0 と同じだった。
- オンラインのメモ書きとオフライン検証を組み合わせた効果。A3・A4 のエージェントは `memory_write` を使わなかった。A4 − A3 は、transcript による検証の寄与を測れていない。
- transcript へのアクセスが偽メモの訂正を可能にしたこと（A3 との比較は交絡している）。
- 記事が報告する改善幅の再現。CL-Bench は 3 反復だけで、向きの一致を確認するにとどまる。
- 他のモデル（より強い agent や consolidator）、より長いストリーム、より多い問題数での挙動。今回の結果は、この実装・このタスク・このモデルの組み合わせに限られる。

## 10. 実務者への示唆

いずれも本実験 1 回の結果に基づく、条件付きの示唆である。

- **記憶を足す前に、記憶なしの基準と比べる。** 今回は、DB を直接確かめられるタスクで、記憶群が記憶なしを下回った。記憶を導入するなら、A0 との A/B 比較を最初に置くべきである。
- **記憶には、事実だけでなく「何を確かめ直すべきか」も書かせる。** 今回の失敗は、古い事実を覚えていたことよりも、確認を省いたことと関連していた。たとえば「コード表は毎回全件を見る」「migration の通知があったら、新しい列とコード表を探す」といった手順を記憶させる方法が考えられる（未検証の仮説）。
- **採点のない統合は、誤った方針を固定しうる。** オフライン処理は transcript 内の DB の応答を根拠にできるが、最終回答への採点フィードバックはないため、エージェントの回答方針が正しかったかは分からない。結果のフィードバックがない場面では、方針は書かせず、観測した事実だけを記録させるほうが安全だと考えられる（推測）。
- **他者が書いたメモを統合するなら、原ログと照合する工程を入れる。** transcript を読めない整理（A3）は、偽メモを「検証済み」に昇格させた。
- **記憶ツールは、提示しても使われるとは限らない。** low effort のエージェントは、検索ツールや書き込みツールを自分からは使わなかった。導入時には、まずツールの利用率を計測する。
